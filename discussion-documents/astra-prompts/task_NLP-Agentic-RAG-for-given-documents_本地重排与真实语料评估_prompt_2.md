# Astra 长任务：检索重排、真实语料对照与第二轮优化

## 我们目前的思路

我们在做 COMP5423 的固定语料搜索 Agent。课程程序需要从同一份 BrowseComp-Plus 语料中检索，使用指定模型完成结果驱动的工具循环，并保留可复核的原文证据、工具轨迹和实际 API 用量。最终表现同时看答题准确率、工具调用次数和 API token。检索的设计目标是让 Agent 在有限预算下更早看到完成下一跳所需的证据。

我们看过项目原有代码和两份设计文档，决定以现有实现为工程底座。它已具备语料导入、索引恢复、三类检索、运行轨迹和评测入口。我们先修了一个明确的接口问题：原来按文档去重，一篇文章只交付一段，同一篇里的另一条关键线索可能在召回时就丢了。现在 `top_k` 按片段计数，三路检索和融合按片段处理，原文位置也通过同步后端传给 Agent。这项改动已经提交到 GitHub。

当前程序流程是：**Agent 提出当前查询 → BM25、E5、Qwen3 指令向量召回 → 片段级 RRF → 返回排名前 k 的原文片段 → Agent 根据证据决定是否继续搜索或读原文。** 同僚负责 Agent 核心，接入工作与本任务并行。我们负责检索侧，先在 RRF 和最终 `top_k` 之间增加本地重排。

之所以先做重排，是因为它可以直接使用当前索引。我们希望先看清两个不同的问题：**关键证据已经召回但排得太低**，以及**关键证据没有进入候选池**。前一种适合改排序，后一种要检查候选深度、检索信号或数据覆盖。直接把候选池加大、换分块、换模型和重排一起做，最后很难知道哪个改动有效。本任务先用对照把原因分清，再根据结果实际完成下一步。

## 第二阶段 实现可关闭的本地重排

### 代码落点

在 `SearchService` 的 hybrid 路径中，在 RRF 之后、最终 `top_k` 切片之前接入本地 Cross-Encoder。三个检索器仍通过唯一的 search 对外提供结果。CLI、仓库现有 Agent 和同僚后端通过同一配置走这条路径。

- 首个模型使用 `cross-encoder/ms-marco-MiniLM-L6-v2`，复用合适的本地 Transformers/PyTorch 依赖。核对[官方模型说明](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2)和[tokenizer 配置](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2/blob/main/tokenizer_config.json)。记录实际使用的模型及 tokenizer revision、设备、批大小和输入上限。
- 将开关、每路候选深度、RRF 后重排深度和重排批大小设为明确的配置。保留旧默认路径，重排默认关闭且延迟加载。禁用状态使用原深度时，查询结果、顺序和分数语义应与基线一致。开启后使用一个单独的可复现配置。
- 输入为本轮 query 和候选原文。保持待重排候选池有界。定义候选不足、重排深度小于 `top_k`、等分以及未经重排尾部的行为。相同重排分数按原 RRF 排名稳定处理。RRF 与重排的原始分数分别用于诊断，公共 `score` 的含义和排序规则应写入说明。
- 对 query、passage 和特殊 token 验证总长度。若需要切窗，使用连续原文窗口并限制窗口数。记录怎样汇总子窗口分数，检查关键片段在窗口尾部时的行为。返回子窗口时同步更新坐标并保留所属 chunk_id。遇到超长输入或模型错误时，记录具体处理及实验受影响范围。
- 对成功重排、显式降级与执行失败留下可区分的记录。模型未加载或分数无效时，实验报告应体现实际发生的路径。重排仅在 RAG 本地运行。

### 对接契约

| 已有入口 | 必须核对的行为 |
| --- | --- |
| `rag_agent.peer_backend:create_backend` | 按现有方式加载检索配置和索引，同僚可直接复用 |
| `search(query, top_k=5)` | 同步、有序平面列表。每条保留 `doc_id/chunk_id/score/snippet/source_url/start/end`。允许重复 doc_id，每个独立片段各计一条 |
| `open_document(doc_id, start=0, length=6000)` | 返回实际原文范围，文档尾部返回实际 end |
| `find_in_document(doc_id, query, window=250)` | 保持已有字面匹配、原文窗口与空结果的行为 |

确认 `document.text[start:end] == snippet`。坐标按原始 Python 字符串计数，范围左闭右开。空命中仍返回 `[]`，失败由既有异常边界处理。重排和三路检索都发生在统一 search 内部。课程工具次数继续按 Agent 发出的实际工具调用统计。

先用合成数据和注入的测试替身覆盖排序与坐标，再用真实模型跑 query–passage 对。用安装后的包或标准入口验证一次 factory 加载、搜索、打开原文和查词。如果同僚的实际 Agent 可用，再验证同文档的两段证据分别保留，选入模型上下文的证据仍带 `chunk_id/start/end`。报告分别写清检索侧测试与同僚 Agent 联调范围。

### 检索对照

| 组别 | 配置 | 回答的问题 |

### 样本与标注

使用 [BrowseComp-Plus 固定语料](https://huggingface.co/datasets/Tevatron/browsecomp-plus-corpus)。已有真实三路索引时优先复用。若没有，固定 revision，先完成真实小样本的导入和三路 smoke，再在可用时间和内存范围内扩大。如果只完成真实 BM25 索引，可用同一重排器在实验入口对 BM25 候选做实测，报告准确标注该检索配置和缺少的覆盖。

优先用确认证据在当前语料范围内的验证题。真实小语料切片可以另行标注少量查询和原文片段，纳入可混淆的候选，并在看实验结果之前固定样本与标注。将调参和最终复核样本分开。把文档级相关性与片段级证据分开记录。有对应标签时计算 Recall@k、MRR 或 nDCG，并写清评估单位。使用部分标签时报告可核对的命中数、排名与案例范围。

参考答案与相关性标注由独立评估读取。可将证据范围用于计算排名指标，查询及排序程序只接收问题与候选内容。分别报告当前语料范围内缺失证据、候选漏召回、候选已命中但排名靠后，以及证据进了 top_k 后的 Agent 答题错误。对不确定的失败留出明确类别。

### 逐题诊断与结果核对

逐题记录用机器可读格式保存即可，避免为此引入新的数据库。可以按下面的字段组织，沿用仓库已有的数据结构和日志工具。

| 字段组 | 至少保留的内容 |
| --- | --- |
| 运行信息 | 查询 ID、实验组、配置指纹、模型与索引标识、成功或错误状态 |
| 候选信息 | 每路候选数量、融合候选的有序 ID、片段所属文档及起止位置 |

| 证据命中 | 标注是否可用、对应证据是否在语料里、是否进入候选池、是否进入最终 top_k |
| 资源信息 | 召回及融合时间、重排时间、总检索时间。真实 Agent 运行另记录实际工具次数、API token 和结束状态 |

先查覆盖，再查召回，再查排序。以有原文范围标注的查询为例，若当前索引里没有对应文档，归为语料覆盖不足。若文档在索引里，但候选中没有覆盖标注范围的片段，查三路召回、分块覆盖和候选截断。若候选中已有对应片段，查它在 RRF 与重排中的名次。若最终结果已有可用证据但 Agent 答错，记录为下游失败，回看真实轨迹是否使用了该片段。判断证据范围命中的规则要在第一轮固定，并注明如何处理跨块证据。

汇总时报告总样本数、有标注的样本数、可用配对数和失败数。分别统计 B 相对 A、C 相对 B 的提升、持平和退化，列出从 top_k 外进入、从 top_k 内掉出的案例。延迟用同一设备、相同预热策略做配对。样本较小时提供逐题数据或中位数，说明高分位数的局限。推荐配置需要结合命中变化和资源成本，并说明结论适用于哪类查询。

| 重排有收益，但本机延迟明显增加 | 优化批处理、候选裁剪或一次运行内的模型复用。优先选剖析显示占时最多的一段 | 对同一候选和查询做预热后对照，同时核对证据排名、耗时和峰值资源 |
| 大量高度重叠窗口挤占名额 | 实现可配置的同文档重叠抑制，并在单独配置中打开。按原文范围判断，保留同文档中位置不同的有效证据 | 对比命中与多样性，检查重复窗口减少后有没有误删关键片段 |
| 样本太小，首轮无法区分原因 | 先补真实语料覆盖、配对样本或候选快照回放，集中复核最常见的失败类别 | 用冻结的新样本重跑关键对照，给出有清楚边界的结论及可复现入口 |

**完成选中的路径再进入交付。** 在代码或配置中落实可复用的改动，或者把缺失的诊断实验做成可运行入口。以第一轮最合适的配置为对照，在未参与选择的样本上做第二轮复核。记录改进数、持平数、退化数与代价。如果尝试的策略退化，可保留复现用的实验配置和报告，推荐有实测支持的版本。涉及重建索引、修改 Agent 核心或扩大付费运行的问题写成后续建议。当前任务仍继续完成验证和推送。

### 第二轮的执行顺序

1. 从首轮结果中选一个能解释最多失败、或能解除主要资源瓶颈的假设。写清需要的改动和预期看到的变化。例如，若长片段尾部的证据在重排后经常掉出，先检查实际评分窗口是否覆盖它。
2. 保留第一轮推荐配置作为对照。为所选改动建立单独配置，固定其余条件。评估一个主变量即可。需要比较参数时，先在调参样本里筛选，再把选中的方案和对照配置放到保留样本上。
3. 把排序收益与系统成本一起看。若片段排名有所改善但重复内容变多，核对多线索题是否损失其他证据。若耗时降低，核对是否仍评分了原先需要覆盖的候选和窗口。
4. 为结论写出复核路径。保留一个改善案例、一个退化或无明显变化的案例及其候选 ID 或运行记录位置。记录第二轮改动最终是作为推荐配置、可选配置，还是仅作为可复现的诊断保留。

## 第五阶段 自行验收、提交并推送

在推送前由你自行做一次独立复查。

1. 从变更差异重新核对任务边界、默认行为、既有索引加载和三个对接函数。重点查重排是否绕过了统一入口、同一文档的两个独立片段是否被覆盖、返回范围是否与文本一致、禁用重排是否会触发模型加载。
2. 核对 B/C 的候选列表一致，第二轮只改变所选因素。检查每张结果表对应的实际运行目录、配置指纹、语料 revision、模型 revision 和样本。确保小样本、全量、真实模型和测试替身的结果都标明范围。合成输出、缺失 usage 或失败题按真实状态报告。
3. 跑现有测试与 Ruff，补足风险点的回归检查。关键项包括关闭重排时的兼容性、确定性同分排序、同文档多片段、Unicode 坐标、长输入、候选不足、空结果和模型故障。发现缺陷后自行修正并重跑受影响的检查。
4. 在仓库的 `docs/` 提交实验报告。写清背景和本任务边界、改动位置、配置、样本与版本、A/B/C 结果、第二轮选择及结果、典型改进与退化案例、推荐配置，以及可直接复制的复现命令。实际原始输出保存在本地忽略目录。仓库记录使用无敏感内容的必要汇总和样本 ID。
5. 核对暂存内容和远端。提交代码、配置、必要测试与实验报告。密钥、课程题目与原文、完整轨迹、模型缓存、数据和索引留在本地。检查 `.env` 和 `.env.openrouter-smoke` 的忽略状态，日志和回复只写变量名。
6. **把最终成果正常推送到目标 GitHub 仓库的功能分支，并核对远端分支指向的 SHA。** 发现远端同名分支有他人改动时，保留其历史，按实际情况安全同步或改用新的功能分支。若认证阻止推送，保留已通过自审的本地提交，并报告准确阻碍和可执行的推送命令。

交付前以组员的视角走一遍报告里的最低依赖复现路线。核对依赖版本、配置路径、运行入口和产出位置。涉及真实模型或全量索引时注明需要准备的资源。确认推荐的实验配置与默认配置的关系，同僚按现有接口接入时能直接知道从哪里开始。
