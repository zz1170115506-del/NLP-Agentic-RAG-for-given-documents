### 3. 并行启动真实语料和索引工作

1. 对照课程数据来源，核对语料 revision、文档计数、唯一 ID、正文、来源 URL、分块策略、Unicode 字符位置和索引 manifest。优先复用完整且指纹匹配的现有索引。完整索引、诊断子集、合成语料使用各自的数据和索引路径。对样本索引注明语料覆盖，不能把小样本构建当全量完成。
2. 用含短文、长文及高分块量的代表性真实样本测量三路吞吐、峰值内存、磁盘占用与预热后查询延迟；分别记录模型下载、语料导入、向量编码、索引写入和查询时间。用实测估算全量，验证中断后恢复、清单兼容和重复运行。对比当前向量分片全扫描的延迟与实际规模，避免以极小合成样本外推。能够运行全量时尽早开始，Agent 的离线开发可与索引构建并行，注意争用资源。
3. **实际完成并验证全量三路索引。** 运行标准入口的单路与混合检索，核对返回文本来自固定语料。若遇到慢或失败，先定位导入、编码、磁盘或检索瓶颈，尝试合理的批大小、设备、缓存、分片或续跑调整，并复测。若仍受硬件、时间或数据访问限制，用实际完成量、估计剩余时间和可执行续跑命令交接。保留最高已验证覆盖，继续开展其它可做的验证，并在返回文档中明确标注全量状态。
4. 实测 `search`、`open_document`、`find_in_document` 的正常及错误路径。检查 `document.text[start:end] == snippet`、同文档多个片段独立计数、排序稳定、空结果、边界分页及查词长度限制。模型只能看见一个检索工具；三路召回、融合、重排等内部操作不增加 Agent 的工具调用次数。

交接语料与索引时保存清单。最少包括固定语料 URL 和 revision、文档覆盖与去重数、分块参数和片段数、两类模型 revision 与维度、设备、索引格式和指纹、构建各阶段耗时、磁盘和查询延迟、重启恢复的核对记录。离开执行机后可用这些信息重建或按课程允许的方式迁移，不把大文件塞进 Git。

3. 对缺失编号、未知或伪造编号、同文档不同段、重复证据、引用坐标偏移、压缩后可见原文范围、坏 JSON、工具失败和耗尽预算写回归。失败原因可定位，修复提示应有边界且复测能证明不会重复无效循环。单题 token、调用数和时间限制是项目设置，比较时固定并报告；所有实际 API 用量仍完整计入。服务缺失 usage 或模型身份不符必须明确记录。
4. 用模拟 HTTP 只验证协议，再用真实 API 验证至少一个从问题到短答案、可核验引用和完整用量的正向样例。对真实事件核验请求、响应、tool call 与结果配对、重试、超时、停止原因、模型身份。若 HTTP 重试也返回 usage，必须计入；未知用量如实标记。避免把网络失败、项目的内部证据质量判定、课程记录格式和答案对错混为一类。用小样本的单题或批次检查验证正式所需的底层条件，同时保留正式 100 题覆盖校验；无需伪造 100 条“正式结果”。

验收时用最小样例逐项核查：检索命中带字符坐标的两个证据；模型在后续请求里看到引用编号与实际可见片段；其最终答案选择这些编号；程序能从早于答案的真实工具结果恢复引用；每次工具和 HTTP 请求都能对账。再故意制造一条坏编号、错误坐标、丢失工具返回、缺失 usage 或伪造 HTTP 事件的测试输入，确认相应检查确实失败。测试夹具始终标明是合成输入，正式运行以原始轨迹为准。

### 6. 分阶段实测，拿到结果后继续做什么

1. **先做真实小样本联调。** 确认真实语料和索引覆盖，再用一题打通指定 API、工具、证据和输出。通过后用约 3–5 道固定题比较基线与 Agent 1.2。固定语料、索引、检索参数、模型及预算，先关闭重排；可以参考 B 的三路 RRF 思路，但不可盲用指向旧机器小语料的路径。至少留一个可追踪的多跳样例和一个失败或边界样例，记录实际成本和有效配对数。合成和 mock 的结果单列。
2. **再运行官方验证集 100 题。** 使用项目的验证集下载入口或课程提供的文件，固定实际 revision，核对 100 个唯一 ID。让最佳可用候选用固定语料真实运行，记录 100 题覆盖、已完成、失败、真实用量及 Normalized EM。用可重跑的小批量启动并续跑到全量，处理可恢复失败；遵守执行机可用的 API 额度。完整验证集可只为正式候选跑一套；其它配置用预先固定的同题子集对比即可。评测参考答案仅由独立评测读取。全量覆盖有缺口时说明范围和原因。
3. **补齐能说明程序表现的对照。** 先使用相同问题做单路与融合的检索对照，再对迭代、上下文、skills 等关键机制做有目的的消融。按成本选择合适的小样本和真实运行范围。记录候选覆盖、证据 Hit@K 或 MRR（仅在有可靠证据标签时）、答案 EM、完成和校验通过率、工具次数、真实 API tokens 及延迟。配置比较逐次只改变一个主要因素；调参样本和复核样本分开。小样本结论注明规模。
4. **按失败位置修一轮并复测。** 语料缺失先补覆盖，候选漏掉查分块、检索路由与候选深度，候选里有而 Top-K 没有查融合或用同池重排对照。证据送达后答错，查候选实体、约束缺口、上下文或语义验证。格式、引用、配对或用量不合格，修输出和审核链路。遇到预算耗尽，先判明重复行动、输入过长、无效重试或外部限额，再改对应环节。完成代码、配置或运行流程的实际修复，再用原失败样例及独立样例复核。
5. **给出有证据的选择。** Agent 1.2 通过正式条件且真实结果有优势时，说明推荐它的理由、成本和回退路径；若基线仍更稳，明确建议及未满足项。Astra 旧报告中 B 在小保留集命中 10/10，C30、D10 各 9/10，只支持关闭重排作为当前对照起点。只有新对照支持时才建议调整。报告推荐候选配置、需要后续确认的门槛和测试入口，最终版本冻结留给 ddg。

每次真实运行使用独立的目录和清单。至少记录代码 SHA、配置指纹、语料和索引身份、问题 ID、预期样本数、实际完成数、异常数、结束原因、运行时间与实际计费用量。先按已授权额度做少量测量，再估算完整验证的消耗。对比时按题匹配，报告两端均可用的配对数以及失败总数；性能汇总不要因排除失败而显得更高。用项目当前的 EM 规则核对归一化和分母。若用保留题评估变更，先确定比较条件和样本，再看结果。

| 观察结果 | 本轮下一步 | 收敛依据 |
| --- | --- | --- |
| 正式轨迹或输出无法核验 | 修复适配或校验流程，重跑一条正向、失败复现和负向回归 | 真实轨迹能复核，坏轨迹仍被拒绝 |
| 官方验证题中语料或索引覆盖不足 | 修复导入与构建，复核文档数和指纹后恢复跑题 | 实际索引覆盖与报告范围一致 |
| 有证据却答错 | 复核 Agent 看到了什么、是否跳过关键约束，测试一项候选或验证策略 | 原失败例和独立复核样本均有记录，比较额外成本 |
| 已有更稳的候选 | 用该配置完成官方验证，复查 skills、界面与批处理，形成推荐 | 给出完整证据、复现命令和仍需 ddg 决定的事项 |
| 资源或权限仍然卡住 | 保存完整可续跑状态，完成不依赖阻碍的功能与验证 | 明确缺了什么、已试哪些修复、恢复后第一条命令是什么 |
