# 三类弃答的根因分析与解决方案

2026 年 11 月 17 日 · 静态分析

本次只阅读任务文档、两份既有复盘和对应版本的代码，没有跑数据、调用 API 或修改程序。下文的数字来自上一轮验收，提出的修法尚待验证。

**建议保留现有的重叠证据保护，优先让程序在每轮搜索后记住“哪个候选还缺哪项条件”。** 同一份记录可以回答三个问题：下一步搜什么、哪些原文值得放进模型请求、当前证据是否足以作答。

## 一、九题结果说明了什么

上一轮使用同一百炼 API 完整重跑后，9 题里有 3 题与参考答案匹配（64、58、788），另外 6 题弃答。这九题选自历史失败案例，适合用于定位故障。

第 788 题最能说明为什么要分层修复。同一次答题中，系统检回了**邻近建筑的建造年份**，但这段原文没有进入最终请求。同时，**医院早已存在**的反证确实进入了最终请求，模型仍用后来的扩建年份回答成立时间。前一处要改证据选择，后一处要改条件核查。最终答案文字虽然匹配，推理中的两处缺口依然可以从记录里找到。

## 二、三类问题及对应修法

| 问题 | 已有记录和代码支持的判断 | 建议修法 |
|---|---|---|
| ① 关键证据搜不到 | 程序已有搜索恢复指引，但停滞次数按每次搜索分别累计。同一轮两次查询都只返回旧片段，就可能在下一轮加载恢复指引后立即关闭工具。上轮 6 道弃答题里，1035、1155、1066 因搜索停滞收尾，960、231、390 则因预留最终回答用量而收尾。 | 对停滞组，在预算足够完成一次探查和最后作答时，给一次实际改查机会。已有候选时，围绕候选和缺失关系搜索或定位文内原句；没有候选时，从题面挑辨识度更高的线索。对预留用量组，把这种定向查询提前。 |
| ② 证据已找到，却没进入模型请求 | 上一版已保护同一文档里的重叠片段。已有 446 条“证据组在某次实际请求中是否可见”的检查记录，其中 394 条完整可见、52 条整组省略、0 条部分可见。剩余缺口在于，来自不同文档、各自证明一个条件的段落仍会竞争有限空间。 | 先为尚缺的关键条件保留能说明它的完整原文，再用剩余空间放补充材料。同一候选既有支持又有反证时，让两方原文都有机会进入最终请求。放不下就记录省略了哪项条件，后续据此回查。 |
| ③ 模型看到证据，仍把条件判断错 | 现有程序能核验引用来自哪篇文档、原文和位置是否正确。技能也已要求逐项核查，但程序没有持续保存各项条件的核查结果。一段真实的医院扩建记录完全可以通过引用检查，却无法证明医院何时成立。 | 对每项题目条件记录候选对象、需要证明的关系、日期或单位，以及支持或反驳它的原文编号。收尾前优先核对会改变答案的矛盾。若明确冲突无法化解，排除该候选；若缺依据的是模型自行添加的解释，删去这句解释。题目明示的条件仍要核查。 |

## 三、建议先改哪里

1. **先改搜索循环对“进展”的判断。** 目前只要搜索返回一段新文字，就可能被计为有进展。建议分别记录“是否找到新片段”和“是否解决了一个条件”。第 390 题需要证明一首歌是目标合辑的第 3 轨。搜到另一篇提及歌名的文章增加了片段数量，但还缺合辑与轨序之间的直接证据。下一次查询应针对这个关系。
2. **再让证据选择读取同一份条件记录。** 保留上一轮已经奏效的同文档重叠片段保护，优先选入能补上不同条件的原文。运行中的条件记录只能引用本轮工具实际返回的证据。旧复盘事后定位出来的文档和参考答案只用于评估。
3. **最后把条件记录用于作答。** 对决定候选是否成立的条件，逐项对照最终请求里实际可见的原文。既检查有没有忽略反证，也检查系统是否因为无关的解释细节而放弃本来有证据支持的答案。第 58 题中，核心资助奖项有直接原文，部分化学史线索则未核实，两者应分别标明。

## 四、后续怎样判断修复是否有效

以下是后续验证建议，本次没有执行。可先用 **1035** 观察恢复搜索能否找到缺失关系，用 **390** 检查系统能否区分“出现歌名”和“证明轨序”，用 **788** 同时检查跨文档原文与反证的使用，再用 **64、58** 检查原有成果是否保住。Qwen 继续搁置。

每题按真实调用顺序记录三个判断：

1. **有没有检回？** 工具是否实际返回能证明该条件的原文？
2. **模型有没有看到？** 这段原文是否出现在实际发给模型的相关请求，尤其是最终请求中？
3. **模型有没有用对？** 最终回答是否准确使用了原文中的对象、事件、时间和关系，是否处理了直接反证？

同时记录答对、错答、弃答、工具调用次数和 API 用量。这样，即便九题总分不变，也能定位改动使哪一个环节变好、哪一个环节仍需处理。
