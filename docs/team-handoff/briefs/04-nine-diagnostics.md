## 2. 九道题逐题还原真实时间线

每题独立写一节，用自然语言先解释问题问什么，再附按发生顺序排列的记录。**每一次 Agent 决策、工具调用和实际 API 请求都要在时间线中有对应行**，重复查询和失败也保留。记录动作及其可观察依据，缺失处标明证据还缺什么。

| 要逐题交代的环节 | 记录要求 |
| --- | --- |
| 接到问题 | 给出验证集题号及题意，把必需的人物、关系、日期、地点、输出格式等拆出来。登记问题实际怎样进入 Agent、初始检索配置、上下文和预算、实际加载了哪些技能。 |
| 每一轮怎么搜、搜到了什么 | 记录轮次与轨迹事件位置、真实工具名、查询或参数、调用 ID、结果数量、关键片段排名、文档和片段 ID、原文字符坐标。标出每次是否增加了新证据、是否重复查询、是否执行 `open_document`、`find_in_document` 或转用其他线索。 |
| 工具证据是否给到模型 | 按轮对照原始工具文本、程序证据状态和实际发给模型的请求。记录关键片段被收录、缩短或省略的时间点，说明当时的上下文限制及可见的证据范围。模型输入以原始 `api_attempt.request.messages` 为准。 |
| 收尾和导出 | 记录停止前剩余预算、停滞或重复动作信号、是否禁用工具、最后一个真实响应和解析／引用检查结果。区分模型直接输出空答、输出协议被拒绝、引用失败以及运行故障。解释最后导出的 `answer` 如何产生，并记录每题总工具数和实际 API token。 |
| 评测器如何给分 | 把最终导出的答案和**官方验证集参考答案**并列，展示双方的规范化结果和严格 EM（0 或 1），具体说明是空答、答案内容不同，还是全名／简称、日期等写法造成差异。说明用于诊断的字面匹配出现在哪一层，并单独判断证据能支持哪些题目条件。 |

评测标签在原始与复测运行结束后才由评测器读取。标签辅助查证只用于离线诊断。记录中可以引用真实轨迹里的工具动作、原文位置、结束说明和公开输出。对系统为何选择某个动作的推断要标为推断。

## 3. 分三类复盘，分别验证第一个故障点

### 第一类（工具未取回完整参考答案）

- 对照每条实际查询和返回片段。用固定全量语料找能支持参考答案的原文，优先按题目中的人名、实体、事件等线索定位。如果用别名、参考答案或已知文档 ID 做辅助定位，单独标注为事后诊断。
- 拿原查询在同一 BM25 上分别重放前 5 和前 20 条，补记历史轨迹实际请求的 `top_k`；再用题目中更具体的实体、时间或关系写一个检索词变体，仅改查询后重放。记录关键原文的实际排名、邻接片段和命中的约束。全量向量索引若已就绪，可用同一旧查询比较覆盖范围，登记检索器、索引身份和结果。
- 区分关键文档没出现、关键片段排太低、候选确实来自别名或相邻段落、参考文字跨片，以及诊断后仍未定位到语义证据。以这一步判定该题应改查询构造、召回方式、候选范围还是片段选择。

### 第二类（工具取回，后续请求里丢失）

- 先确认命中的文字能支持题目条件。用 `doc_id/chunk_id/offset` 锁定该片段，从工具返回对照状态快照，再对照此后的实际请求。指出首次消失的位置、当时的上下文字符数，以及可证实的原因。检查候选去重、证据内存状态、证据排序、裁剪和整组工具消息移除。
- 优先用原轨迹离线重放上下文选择。做一个最小对照，仅调整关键片段的选择或保留方式，维持同一预算，记录它是否重新进入实际请求。若再实测答题，分别报告进入请求、最终有答案及 EM。必要定位对照可以临时保留原工具已经返回的证据，明确标为诊断条件。

### 第三类（请求已有参考文字，仍弃答）

- 建一张条件表。逐项列出条件、可见支持证据、反证或缺口；核对同名人物、同年不同事件和同一数字对应的关系。判断原文实际证明到了哪一步。
- 查看确定候选后每一步操作、查询重复、文档读取及 `finalization`。若缺某个条件，先用「候选实体 + 缺失条件」做一次离线定向查询，必要时在固定语料打开原文或文内找词，说明是否找到足够证据。有新证据时可做单变量复测，记录真实的下一步搜索与结束状态。
- 若条件皆有充分证据，检查最后原始模型响应及解析、校验、导出的顺序，定位空答出自模型还是程序后处理。结论中写清哪一种解释有日志支持，哪一种还待验证。

## 4. 在 Astra 机器配置百炼并做复测

请用 ddg 私下提供的百炼 API Key 配置 Astra 机器当前工作区的 Git 忽略 `.env`，文件权限只允许当前账户读写。下面用的是已在 Lex 本机验证过的北京接入地址。如果你的账号必须使用业务空间专属域名，从实际授权的百炼北京控制台获取 `base URL`。Key 只随请求发给已核实的百炼北京地址。保持旧官方兼容运行的配置、预测和使用的密钥可在其原位置作历史复核，使用独立的新输出目录运行百炼。

```dotenv
LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=deepseek-v4-flash-0731
LLM_MODEL_VERIFIED=true
LLM_MODEL_VERIFICATION_NOTE="Alibaba Cloud Model Studio Beijing GA 0731, https://help.aliyun.com/zh/model-studio/deepseek-api"
LLM_API_KEY=<ddg 私下提供的百炼 Key>
```

1. 使用 `configs/course-full-sparse.yaml` 或参数一致的专用配置，检查模型策略为 `course_pinned`，核对环境变量优先级、实际主机与模型 ID。发一个短请求和一个小型的项目工具往返，记录 HTTP 状态、真实响应模型、工具调用 ID 配对及各次 `usage.total_tokens`。写明实际 thinking 设置。百炼接口可用 `enable_thinking` 控制，采用前核对现有适配器真正发送的 payload，做对照时记录差异。[百炼 DeepSeek API 文档](https://help.aliyun.com/zh/model-studio/deepseek-api) · [北京接入说明](https://www.alibabacloud.com/help/en/model-studio/beijing-access-information)
2. 联调通过后先用同一 BM25、同一 Agent 和预算复跑九题，生成单独的百炼基线。历史 V4.1 与本次百炼的模型和服务商均不同，记录这种差异。需要验证修复时，以本次百炼基线作对照，每次只变更一处。保存仅题号和题目送入 Agent 后产生的完整轨迹，跑完才做 EM。标记任何借助标签定位的实验。
3. 逐题列出历史结果、百炼基线和单变量复测结果。记录是否取回支持证据、是否送给模型、是否覆盖题目条件、是否回答、是否匹配、重复搜索、工具数和实际 token。出现额度、网络或模型身份问题时记录现象和实际完成范围，继续离线复盘。全程使用官方验证集。
