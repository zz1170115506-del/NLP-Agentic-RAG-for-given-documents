## 5. 三类检索：都要有真实实现

### 5.1 Sparse retrieval

- 实现可持久化的 BM25，例如 BM25S 或经说明适合当前规模的方案。
- 支持索引建立、加载、查询，明确 tokenizer 和分词设置。

### 5.2 Encoder-based dense retrieval

- 使用 E5/BGE/GTE 等 encoder-based embedding 模型中的一个，完成真实 embedding、持久化向量索引和查询。
- 按所选模型规范实现 query/document 前缀、pooling、归一化和相似度。不得用随机向量或 hash 特征冒充 dense 模型。

### 5.3 Instruction-aware LLM embedding retrieval

- 使用 Qwen3-Embedding 或 E5-Mistral 等 **LLM-based embedding** 模型，真正将检索任务 instruction 应用于 query 编码。
- 核对官方模型卡与所需库版本，实现该模型正确的 instruction 模板及编码方式。不能只给普通 encoder 添加一段指令就声称属于第三类，也不能复用第二类向量冒充第三类。
- 选用规模合理、可配置的模型；支持 CPU/MPS/CUDA 中实际可用的设备，不假定用户拥有独立 GPU。

### 5.4 长文档、索引与融合

- 文档可能超过 embedding 最大长度，提供可配置的分块与重叠，避免静默截断只检索长文档开头。
- chunk 保存 `doc_id/chunk_id/offset` 等稳定溯源信息；检索结果汇聚、去重到文档级，保留命中片段和对应原文位置。
- 使用 FAISS CPU 或其他有明确理由的持久化向量索引。避免在网页每次查询时重建索引或重新编码整个语料。
- 索引 manifest 保存模型 ID/版本、语料指纹、分块、维度和归一化等关键参数；加载时检查兼容性。
- 支持单方法对比，以及三方法融合，例如 RRF。不要直接相加量纲不同的原始分数。
- 支持小样本限制、批次大小、增量/断点恢复或可重用的分片，以及进度与耗时信息；全量规模不得一次性把全部文档和所有中间表示装入内存。
- 真实实现与真实验证分别报告。环境无法下载某模型时保留可执行实现与精确运行命令，但明确标记该模型尚未完成真实 smoke test，不能记为“三类均验证通过”。

## 6. 工具层：恰好一个检索工具

agent 可见的检索工具只能有一个，例如：

```text
search(query, top_k, method="hybrid")
  -> ranked results: doc_id, score, snippet, url, hit metadata
```

- `method` 可支持 sparse/encoder/instruction/hybrid，或内部配置选择；不能再暴露 `bm25_search`、`dense_search` 等独立检索工具。
- agent 另需能调用支持工具。至少实现 `open_document(doc_id, offset, limit)`，建议再实现 `find_in_document(doc_id, text, ...)`。
- 实现 `load_skill(name)` 或等价运行时加载机制，与自动 skill 选择闭环连接。
- 每个实际工具有清楚的名称、用途、输入 schema、输出 schema、错误格式、边界验证及运行实现。工具注册表应成为模型 schema、分发器和文档的共同来源。
- 限制打开文档的返回长度并支持分页，返回证据位置。数据不存在、非法参数和空结果应变成可供 agent 恢复的结构化结果。
- 源码中不能调用任意 shell 来模拟“工具”。网页也不暴露不必要的文件系统或命令执行功能。
- 文档中明确实际工具类型数，只统计已实现且 agent 可调用的工具。

## 7. Agent loop 与独立上下文管理

### 7.1 真实结果驱动的迭代

- 模型读取问题，决定是否加载 skill、选择工具并生成参数；执行后根据返回结果决定下一步，直到输出最终答案或达到预算。
- 必须支持后续搜索依赖先前结果，例如先找到实体、再搜索其关联信息；不能固定执行一次检索后生成，也不能用写死的检索步骤冒充模型选择。
- 设置最大迭代轮数、工具调用数、LLM 输出长度/预算、超时和重复无效行动检测。所有退出路径记录明确的 stop reason。
- 正式回答应通过文档证据支持。证据不足或运行失败需明确记录，不编造引用或装作成功完成。
- `answer` 保存适合 normalized EM 的简短答案字符串；网页中的解释、引用、状态另行展示，不把整段推理和来源列表塞进 answer。

### 7.2 结构化状态与上下文预算

- `AgentState` 独立于原始消息列表，至少包含问题、已访问文档、已选证据、活动子查询/搜索进展、候选答案、已选 skills、预算/计数和终止状态。
- 证据包含文档 ID、原文片段和位置；不得凭空制造原文。状态更新需经过校验。
- 实现真实上下文控制，至少包括证据去重、相关片段选择和预算裁剪；可增加压缩，但不要把所有消息及工具输出无限追加给模型。
- 分离完整、追加式的运行轨迹与每轮真正发送给模型的精简上下文，裁剪上下文不得删除审计记录。
- 裁剪后保留 API 要求的 tool-call / tool-result 消息配对，避免因删除消息形成非法工具会话。
- 网页可展示结构化行动摘要和状态，不要求模型输出隐藏思维链，也不补写不存在的推理内容。

## 10. 预测输出、轨迹、统计与评测

每个输入问题恰好产生一条记录，正式文件名为 `test_prediction.jsonl`：

```json
{
  "id": "string",
  "question": "string",
  "answer": "string",
  "trajectory": [],
  "tool_calls": 0,
  "total_tokens": 0
}
```

上面只是字段结构，不是允许编造的预测。实现要求：

1. `trajectory` 保存实际发生的完整过程，按时间顺序，机器可读。优先兼容官方样例的消息式结构，并补充必要状态、skill、裁剪和错误事件。保存真实请求上下文、响应、工具参数/返回以及 call ID 对应关系；敏感凭据必须脱敏。
2. 所有实际 LLM 调用，包括另行进行的选择、重试修复、验证或压缩调用，都必须记录并累计 API 返回的 `usage.total_tokens`。不使用字符数或本地估算冒充正式 token 统计，不对 prompt/completion/cache/reasoning 字段重复求和。
3. 成功返回 usage 的重试也要计入。若服务未返回可靠 usage，应明确报错或标记该运行不满足正式提交条件，不能填 0 装作完整统计。
4. `tool_calls` 按 agent 发出的每一次工具调用计数，包含支持工具和 agent 发起的 skill 加载等实际工具调用；失败、无效参数、重试调用也不应被隐去。检索工具内部调用三个 retriever 仍只算一次 agent 工具调用。非工具形式的内部发现、路由、向量计算不算工具调用。
5. 批量入口支持逐题落盘、断点续跑、ID 去重和恢复校验。重启不能重复输出；保留原始 id，不将数字样式字符串误转为另一 ID。
6. 对失败题保存真实失败轨迹和独立状态说明，提供重跑入口；不要丢掉题目，也不能用伪造回答或模板成功轨迹凑齐记录。未完成指定模型真实流程的失败记录不得被验收器判成合格正式提交。
7. validator 检查字段及类型、整数非负、ID 唯一性、题目一致性、输入全覆盖、无额外记录、轨迹配对、统计与实际记录一致。正式测试应恰好覆盖输入的 100 题；小样本调试不能被误报为正式测试通过。
8. 实现课程 normalized EM：lowercase、去标点、移除英文冠词 a/an/the、归一化空白后精确匹配。参考答案只在独立 evaluator 中加载，不传入 agent。

## 12. 必要验证与诚实交付
